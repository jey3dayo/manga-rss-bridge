# Pixivコミック作品フィード設計

## 目的

Pixivコミック作品ページから公開されている作品・話数メタデータを取得し、既存の manga-rss-bridge と同じ形式のRSSを提供する。対象作品8789を FreshRSS に登録できる状態にする。

## 利用者向けインターフェース

- ルート: `/pixiv-comic/<work-id>.xml`
- 例: `/pixiv-comic/8789.xml`
- FreshRSSのOPML登録処理は既存のものを使い、登録後に更新と記事取得を検証する。

## データフロー

1. Pixivコミック公式フロントエンドが使用する作品情報API `GET /api/app/works/v5/{workId}` を取得する。
2. 話数一覧API `GET /api/app/works/{workId}/episodes/v2` を取得する。
3. Zodで外部レスポンスを検証し、公開メタデータのみ `MangaFeed` に変換する。
   - フィード名: 作品名
   - アイテム名: 話数番号とサブタイトル
   - アイテムID: episode ID
   - 公開日時: `read_start_at`（Unix epoch milliseconds）
   - アイテムURL: `viewer_path` を `https://comic.pixiv.net` に結合した公式ページ
4. 既存RSS rendererでXMLを生成する。

実地確認では、作品8789の2つのAPIは匿名アクセスでHTTP 200となった。話数APIは18行を返すが、未公開プレースホルダーを含み、実際の話数データは一部行だけにある。`state` が公開可能（`readable`）で、`episode` と正の `read_start_at` がある行だけをRSSアイテムにする。APIは公式Webフロントエンドの公開エンドポイントだが、安定性保証のない内部APIとして扱う。

## 境界・安全性

- 閲覧本文、ページ画像、購入情報などは取得・配信しない。RSSには公式の公開話数メタデータとリンクのみを載せる。
- ログイン必須のpreview APIや、アクセス制御を回避する処理は使わない。
- API応答の形式変更・空配列・欠落値はスキーマ検証でエラーとして扱い、壊れたフィードを返さない。
- 作品IDをルート境界で検証する。

## テスト

- fixtureに対する作品・話数レスポンスのスキーマ検証。
- 話数タイトル、日付、ID、公式リンクの変換テスト。
- 不正なID、空・不正なレスポンス、取得失敗のエラー伝播テスト。
- プロバイダー登録後にローカルHTTPルートがRSS 2.0を返すことを確認。
- デプロイ後、FreshRSSからHTTP 200で取得され、8789のフィードに記事ができることを確認。

## 未解決事項

- APIは公式ドキュメントのないフロントエンド用エンドポイントであるため、実装後も実際のクラスタから取得できることを検証する。
- 話数一覧APIが返す件数や順序は固定と仮定せず、全行を検査して公開済みの話数だけをRSSアイテムに変換する。
